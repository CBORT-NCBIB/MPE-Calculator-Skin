# End-to-End Testing

This project ships an end-to-end test suite that exercises the real `web/index.html` in a real headless Chromium against the real React, Recharts, and echarts CDN stack. The suite runs locally via `npm run test:e2e` and on every push and PR via GitHub Actions.

## What's covered

Twenty-five tests across four spec files:

| Spec | Tests | What it verifies |
|---|---:|---|
| `tests/e2e/smoke.spec.ts` | 3 | Framework smoke: React mounts, the Scanning Protocols tab renders, no console errors during initial load |
| `tests/e2e/preset-import.spec.ts` | 7 | Preset LSP-JSON import path: importing `test1-preset-raster.lsp.json` populates wavelength, beam diameter, scan width, scan height, and line count; eject restores pre-import state |
| `tests/e2e/custom-import.spec.ts` | 8 | Custom-segments LSP-JSON import path: square-at-offset and 4×3 zigzag fixtures populate width/height correctly with `lines=1` (custom path) and eject restores state |
| `tests/e2e/error-import.spec.ts` | 7 | Schema-validation-error path: malformed fixture produces "Import failed" badge, "3 errors ▾" indicator, structured error rendering, Eject and Import buttons remain visible (bug #10 canary), form fields are not mutated (atomicity), eject restores `Preset: Built-in` |

This covers all three branches of `_lspApplyState` in `web/calculator.jsx` (preset, custom, error) plus the framework-smoke checks. The tests run against the same `web/index.html` that a deployment would ship — no mocks, no shimming.

## How to run locally

After cloning the repo, install the root-level dev dependencies once:

```bash
npm install
npm run test:e2e:install
```

The first command installs `@playwright/test`. The second downloads the Chromium binary and its Linux system dependencies (the binary download is roughly 150 MB; the extracted install is larger). Both commands are idempotent; re-running them is harmless.

Then run the suite:

```bash
npm run test:e2e
```

Expected: `25 passed (Xs)` in roughly 5–15 seconds on a modern laptop, depending on Chromium startup time and CPU load.

### Variants

```bash
npm run test:e2e:ui                                # interactive UI mode (best for debugging)
npx playwright test --headed                       # see the browser
npx playwright test --debug                        # step-through debugger
npx playwright test tests/e2e/error-import.spec.ts # run one spec
npx playwright test -g "atomicity"                 # run tests matching a pattern
```

After a failed run, the HTML report contains screenshots, traces, and videos:

```bash
npx playwright show-report
```

## Architecture

### Web server

Playwright spawns Python's built-in `http.server` on port 4250 (`playwright.config.ts:webServer`) to serve `web/`. Python rather than a Node static server because Python is already a build dependency — no need for `serve` or `http-server`.

### Browser

Chromium only. Firefox and WebKit can be added later if cross-browser coverage becomes valuable; for now Chromium is sufficient to catch the kinds of regressions e2e is meant to catch (React state, DOM events, file-input handling, schema validation pipeline).

### Fixtures

LSP-JSON test files live in `tests/e2e/fixtures/`:

- `test1-preset-raster.lsp.json` — valid preset path (`scanParams` populated)
- `test2-custom-square-offset.lsp.json` — valid custom path (`engineSegments` with a square at an offset)
- `test3-2d-zigzag.lsp.json` — valid custom path (4×3 zigzag)
- `test4-malformed.lsp.json` — schema-invalid (missing `pulse_duration_s` when `pulse_mode = "pulsed"`)

The first three fixtures were generated by the LSPFactory tool; the malformed fixture was hand-authored to exercise a specific schema violation. Each fixture exercises a specific branch of the import pipeline. Add a new fixture by placing a `.lsp.json` file alongside these and referencing it from a spec — either generated via LSPFactory or hand-authored, whichever is more convenient for the case under test.

### CI awareness

`playwright.config.ts` detects `process.env.CI` and adapts:

| Setting | Local | CI |
|---|---|---|
| `forbidOnly` | `false` | `true` (fails the build if any test is `.only()`) |
| `retries` | `0` | `2` |
| `workers` | one per CPU | `2` |
| `reporter` | `list`, `html` | `github`, `list`, `html` |
| `reuseExistingServer` | `true` | `false` |

The `github` reporter emits inline annotations on PR diffs when a test fails, pointing to the file and line of the failing assertion.

## How to add a new test

1. Pick the right spec file (or create a new one). Most new tests fit in an existing spec.
2. If the test needs a new fixture, add a `.lsp.json` file under `tests/e2e/fixtures/`.
3. Write the test following the existing patterns.

A minimal new test, structurally. The shared `gotoGeneralScanningTab` and `getLspFileInput` helpers live in `tests/e2e/helpers.ts` and are re-used across all three import specs; new tests should import them from there.

```ts
import { test, expect } from "@playwright/test";
import { resolve } from "node:path";
import { gotoGeneralScanningTab, getLspFileInput } from "./helpers";

const FIXTURE_PATH = resolve(__dirname, "fixtures/my-new-fixture.lsp.json");

test.describe("My new behavior", () => {
  test("does the thing", async ({ page }) => {
    await gotoGeneralScanningTab(page);
    await getLspFileInput(page).setInputFiles(FIXTURE_PATH);

    // For a successful import, the badge text format is:
    //   "Imported: <filename>"                  (preset path)
    //   "Imported: <filename> (custom path)"    (custom-segments path)
    // For a malformed file, the badge text is exactly "Import failed".
    //
    // Use an anchored regex to match the expected format precisely so
    // a regression in the preset/custom flag is caught.  See the
    // existing specs for examples.
    await expect(
      page.getByText(/^Imported:\s*my-new-fixture\.lsp\.json$/)
    ).toBeVisible({ timeout: 15_000 });
    // assert whatever new behavior you're testing
  });
});
```

Run the new test in isolation while developing:

```bash
npx playwright test -g "does the thing" --headed
```

### Selector conventions used in the existing suite

- **Form fields** are addressed by their stable IDs (`#scan-wl`, `#scan-dia`, `#scan-sw`, `#scan-sh`, `#scan-nl`, etc.). These IDs are part of the contract — if you rename them in `calculator.jsx`, update the specs.
- **Buttons** use `getByRole("button", { name: "...", exact: true })`. The `exact: true` flag prevents fuzzy matches like "Eject" matching "Re-eject".
- **Text-content assertions** use `getByText("...", { exact: true })` whenever there's any risk of an ancestor element's concatenated text matching as a substring (this came up in the error-panel rendering of the error-import spec).
- **File inputs** are addressed by `input[type="file"][accept*=".lsp.json"]`. There's only ever one such input in the DOM regardless of which sub-tab is active.

### Things to avoid

- **Don't use `.only()` in committed code.** CI has `forbidOnly: true` which will fail the build if it sees a focused test. If you need to focus on one test during development, use `npx playwright test -g "pattern"` instead.
- **Use `.skip()` sparingly and with a comment explaining why.** Skipped tests should not be silently accepted as the status quo; they should be re-enabled or removed as soon as the underlying reason is resolved.
- **Don't sleep.** Playwright's auto-retrying assertions (`expect(...).toBeVisible()`, `toHaveValue()`, `toHaveCount()`) wait for the condition; an explicit `setTimeout` is almost always wrong and causes flakes.
- **Don't assume fixture order.** Each test gets a fresh browser context — no state leaks between tests. If your test depends on a prior test having run, you've designed it wrong.

## Common failure modes

### `getByText("...").toBeVisible()` times out

The text isn't appearing in the DOM. Possible causes:

- A previous setter never fired (check the React state path)
- An async operation didn't complete (network, Worker)
- The selector is too specific (`exact: true` when whitespace differs)

Use `--debug` mode and step through to see exactly what's rendered when the assertion times out.

### `setInputFiles()` doesn't trigger the React handler

Playwright's `setInputFiles` dispatches `input` and `change` events on the file input element and awaits the resulting event handlers. If React's `onChange` handler isn't firing, the file input you selected might be the wrong one. Check the accessibility tree:

```ts
const inputs = await page.locator('input[type="file"]').all();
for (const i of inputs) console.log(await i.getAttribute("accept"));
```

There should be exactly one matching `accept*=".lsp.json"` on the General Scanning sub-tab.

### Tests pass locally but fail on CI

The most common cause is timing. The Playwright config retries failed tests twice on CI (locally, zero retries — failures are loud). Playwright captures debugging artifacts as follows:

- **Screenshots** on every failing attempt (`screenshot: "only-on-failure"`)
- **Traces and videos** during the first retry attempt (`trace: "on-first-retry"`, `video: "on-first-retry"`)

So if a test fails on the initial attempt and then passes on the first retry, you'll have a screenshot of the initial failure plus a trace and video of the (now-passing) retry — useful for diagnosing what the CI environment looks like. If both attempts fail, you'll have screenshots from each and a trace/video from the retry.

Common culprits: slower CI runner, network latency to CDN, race between React state updates.

CI uploads the `playwright-report/` and `test-results/` directories as a GitHub Actions artifact on failure. Download it from the workflow run summary page and run `npx playwright show-report path/to/extracted/playwright-report` locally to inspect.

### Schema validation fails for a different reason than expected

The error-import spec asserts on a specific error message (`Missing required field: pulse_duration_s`) and on the count being exactly 3 (one from each `oneOf` branch that Ajv tries). If the schema is changed and the resulting error set differs (different message, different count), the test fails — this is intentional. Re-examine whether the schema change is correct, then update the assertion if it is.

## Continuous integration

The `e2e-tests` job in `.github/workflows/ci.yml` runs on every push to any branch and every PR to main. It:

1. Checks out the repo
2. Sets up Node 20 and Python 3.12
3. Installs Babel (for `web/build.py`), builds `index.html`, installs Playwright
4. Resolves the exact Playwright version and uses it as a cache key for the Chromium binary
5. Installs Chromium (or restores from cache) plus system dependencies
6. Runs `npm run test:e2e` with `CI=true`
7. On failure, uploads `playwright-report/` and `test-results/` as an artifact retained for 14 days

The job is independent of the other CI jobs (it does not block `build`, nor is it blocked by `python-tests` or `js-tests`). Its failure fails the overall workflow status — there is no `continue-on-error`.

Expected total CI runtime is on the order of a minute or two on cache hit, and a few minutes on cache miss (first run after a Playwright version bump). Exact times depend on runner availability and load.
